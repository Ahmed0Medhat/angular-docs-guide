# Accessibility (a11y)

> Sources (angular.dev, v22.3 @ bd1e32b): Accessibility — https://angular.dev/best-practices/a11y.

## When to use
- Binding static or dynamic ARIA attributes and element-reference ARIA properties in templates
- Building custom components (buttons, links, text inputs, progress bars) that stay accessible
- Managing focus after router navigation and marking the active link for screen readers
- Announcing lazily loaded (`@defer`) content to assistive technologies
- Picking ready-made accessibility tooling: Angular Material, CDK `a11y`, Angular Aria
- See also: ARIA attribute binding syntax and `@defer` accessibility → references/guide/templates.md
- See also: headless accessible directives (Angular Aria) → references/guide/aria.md
- See also: `RouterLinkActive` and router events → references/guide/routing.md

## Rules
- MUST use attribute binding to control accessibility attribute values; ARIA attributes bind like any other HTML attribute (`[aria-label]="..."`), and static ones are written as plain attributes.
- MUST use property binding for ARIA APIs/inputs that take structured values such as arrays of `Element` references (e.g. `[ariaLabelledByElements]`), so the relationship stays in sync.
- PREFER reusing native elements over re-implementing their behavior: build custom buttons/links as components with an attribute selector on a native `<button>` / `<a>`.
- PREFER a container component that projects the native control (e.g. an `<input>`) via content projection, so consumers can still set any attribute/property on it.
- PREFER host bindings to set `role` and ARIA attributes on custom widgets; let the consumer provide `aria-label`.
- MUST decide where focus goes after each navigation and move it there on `NavigationEnd`; it should land where users can immediately reach the newly routed main content.
- AVOID letting focus fall back to `body` after a route change.
- PREFER `ariaCurrentWhenActive` on `RouterLinkActive` links so the active link is exposed via `aria-current`, not only by a CSS class.
- MUST wrap `@defer` blocks in elements with suitable ARIA live regions so screen readers announce the loaded content.
- PREFER Angular ESLint accessibility lint rules to check code against accessibility standards.

## API cheat-sheet
| API | Purpose | Notes / version tag |
|---|---|---|
| `[aria-*]="expr"` / `aria-*="text"` | Dynamic / static ARIA attributes | Attributes lowercase (`tabindex`), properties camelCase (`tabIndex`) |
| `[ariaLabelledByElements]="[a, b]"` | ARIA relationship by element references | Property binding with template refs |
| `host: {role: ..., '[attr.aria-valuenow]': ...}` | ARIA on a component's host element | Used in the progress bar case study |
| `LiveAnnouncer` (CDK `a11y`) | Announce messages via an `aria-live` region | Angular CDK |
| `cdkTrapFocus` (CDK `a11y`) | Keep Tab focus inside an element | e.g. modal dialogs |
| Angular Material | Reusable UI components aiming to be fully accessible | Maintained by the Angular team |
| Angular Aria | Headless directives for WAI-ARIA patterns (accordion, combobox, listbox, menu, tabs, toolbar…) | Handles keyboard, ARIA, focus, screen readers |
| `NavigationEnd` | Router event to trigger focus updates | From `Router.events` |
| `RouterLinkActive` `ariaCurrentWhenActive` | Sets `aria-current` to the given value on active links | e.g. `"page"` |

## Patterns

### Element-reference ARIA
```angular-ts
@Component({
  template: `
    <h2 #title>Check your answers</h2>
    <p #desc>Review before submitting.</p>
    <section role="dialog" [ariaLabelledByElements]="[title, desc]"><ng-content /></section>
  `,
})
export class ConfirmDialog {}
```

### Accessible custom progress bar
```ts
@Component({
  selector: 'app-meter',
  template: '<div class="fill" [style.width.%]="value()"></div>',
  host: {
    role: 'progressbar',
    'aria-valuemin': '0',
    'aria-valuemax': '100',
    '[attr.aria-valuenow]': 'value()',
  },
})
export class Meter {
  value = input(0);
}
```
```html
<app-meter [value]="progress" aria-label="Upload progress" />
```

### Focus after navigation
```ts
router.events.pipe(filter((e) => e instanceof NavigationEnd)).subscribe(() => {
  document.querySelector<HTMLElement>('#page-heading')?.focus();
});
```

### Active link for screen readers
```html
<nav>
  <a routerLink="home" routerLinkActive="current" ariaCurrentWhenActive="page">Home</a>
  <a routerLink="about" routerLinkActive="current" ariaCurrentWhenActive="page">About</a>
</nav>
```

## Pitfalls
- A component whose template only contains an `<input>` hides it: consumers cannot set arbitrary attributes/properties on it; use projection instead.
- `RouterLinkActive` classes are visual only; blind and low-vision users need `aria-current`.
- Screen readers may not announce content when a `@defer` block finishes loading unless it sits in a live region.
- Relying on visual cues alone after navigation leaves keyboard and screen-reader users without a focus target.
